# 问序｜测试计划与方法

## 1 验证目标与分层

验证第一阶段业务规则、MongoDB 直接约束以及失败和并发时的数据一致性。规则依据见[系统说明](../02_文档/01_系统说明.md)、[数据库设计](../02_文档/02_数据库设计.md)和[关键逻辑](../02_文档/04_关键逻辑说明.md)；各组输入、步骤、预期和源码入口见[覆盖表](02_用例覆盖表.md)，实际运行结论见[执行结果](03_执行结果.md)。

| 层次 | 输入与观察 | 主要验证内容 |
|---|---|---|
| 请求模型、领域函数 | 直接调用，检查结构或异常 | 类型、空值、边界、标准化及跳转优先级 |
| 数据库直接集成 | 绕过 HTTP，直接读写真实 MongoDB | 验证器、索引、非法更新原子性、重复初始化 |
| API 集成 | 请求真实应用，同时比较数据库状态 | 权限、状态、匿名、重复资格、事务、统计及并发 |
| 前端纯函数 | Node 测试 | 稳定 ID、引用清理、表单序列化与答案变化判断 |
| 浏览器端到端 | Edge 操作真实页面及接口 | 完整业务闭环、响应丢失恢复、重新认证及布局 |

字段边界主要放在函数测试，跨集合结果放在数据库和 API 测试，浏览器保留完整流程和关键恢复场景。静态托管另由 `test_frontend_support.py` 验证；缺前端构建时可跳过，须如实记录。

## 2 用例设计与断言

| 方法 | 代表设计及检查点 |
|---|---|
| 等价类与边界值 | 四题型区分有效、非法、允许留空；覆盖数量和长度上下界、Unicode、有限数与安全整数、截止前／等于／后 1 ms |
| 决策表 | 匿名／实名 × 允许／禁止重复；两个不同 key 的独立提交与同 key 重试分开检查，完整结果见覆盖表 REPEAT-01 |
| 状态与权限组合 | 草稿／发布／关闭，结合本人／他人、新／旧 revision、截止前／后；拒绝时检查原数据未改变 |
| 故障注入 | 隔离库收紧答卷验证器，让参与记录插入后答卷失败；检查参与记录和 revision 一同回滚，恢复后原资格仍可提交 |
| 受控并发 | 屏障或事件控制两个请求的竞争位置；检查同 key、不同 key 以及手动关闭竞争，不以任意 sleep 猜测先后 |

例如禁止重复时，同账号预先取得两个 key 并发提交，预期恰好一个 201、一个 409，最终只有一份答卷和一条参与记录。只检查状态码不足以证明原子性，还需核对保存的 key、答案及 revision 对应成功请求。

断言使用可独立推导的值，例如数字 10、30 的均值应为 20，不调用被测算法生成预期。成功检查规范化内容与允许变化的字段；拒绝或重试比较数据库快照，观察答卷、参与记录、账号及无关问卷是否保持原状。

截止边界使用可控时间输入，不修改系统时钟。关闭竞争的两种控制顺序及四策略组合见[专项说明](04_关闭与提交竞争专项.md)。

## 3 数据库与业务责任边界

| MongoDB 直接保证 | 业务层另行保证 |
|---|---|
| 必填字段、BSON 类型、枚举、嵌套结构、额外字段和容量限制 | 所有权、发布冻结、跨字段上下限、合法完整路径 |
| 指定数组的 `uniqueItems` | 同一文档内按题目／选项／规则 ID 判重 |
| 用户名键、分享标识、问卷＋key、问卷＋用户的唯一索引 | 标准化后同 key 幂等、匿名身份字段、跨集合引用与事务 |

API 返回 422 不能单独证明 MongoDB 验证器有效，因此直接数据库测试绕过应用检查。结构合法但业务非法的代表文档需在领域入口拒绝；重复初始化则检查既有数据、索引和验证器仍有效，不视作历史数据修复或迁移。

## 4 隔离、执行与证据

集成 fixture 启动真实 MongoDB 单节点副本集，使用独立端口和随机测试库；`_env_file=None` 禁止读取本地配置，每项结束只删除自己的库。浏览器启动器同样使用隔离服务。故障注入和并发测试均在该环境执行；响应丢失场景是服务器真实保存后中断浏览器响应。

建议先运行领域与前端纯函数，再运行数据库、API 和浏览器。统一命令见[测试入口](README.md)。运行器记录源码 SHA-256、开始结束时间、退出码、各套件统计及运行期间源码是否变化；原始 JUnit、控制台和浏览器报告保留在独立运行目录。失败、跳过、未运行和环境阻塞分别记录，修正后重跑受影响范围。

覆盖表使用稳定业务组 ID；一组可映射多个函数，一个参数化函数可展开多项，一函数也可支持多个组。统计以执行报告为准，结论仅覆盖列出的输入和控制顺序，不代表所有线程交错、性能、安全或 100% 代码覆盖。
