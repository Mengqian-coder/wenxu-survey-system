# AI 使用日志

使用的 AI：ChatGPT  
整理日期：2026 年 10 月 20 日

以下根据实际交流整理，Prompt 为原提问的摘录或概括。“修改”记录我提出的要求、判断及调整，代码和测试中的 AI 协助如实注明。

## 交互过程

### 1. 明确匿名的含义

**Prompt:**
我们先来讨论问卷系统规则的设计，首先我认为匿名指的是登录之后不记录身份。先完成规则明确，给出规则设计，希望一起讨论。

**Result:**
AI 协助梳理登录、匿名填写和答卷身份信息之间的关系，形成业务规则草案。

**修改：**
我提出“登录之后不记录身份”，并确定整份问卷统一匿名或实名：填写者需要登录，匿名答卷不保存身份引用，将认证与答卷身份存储分开。

### 2. 限定发布修改和题目跳转

**Prompt:**
规则中关于发布和跳转的设计，我认为问卷系统不接受发布以后修改题目、选项和规则；支持只向后跳转，修改前面答案之后清空后续答案。

**Result:**
AI 据此整理问卷发布后的结构限制、跳转方向和历史答案处理方式。

**修改：**
我要求发布后冻结题目、选项和规则，保持历史答卷题意稳定；只向后跳转以避免循环，修改前题后清空后续答案以免旧路径残留。AI 后续细化为“答案实际变化才清空”，区分查看与修改。

### 3. 核查未保存内容是否必须恢复

**Prompt:**
关于问卷系统所有填写都应该被保存的描述，帮我查找实验文档中的要求和说明，他的意思是否是要求没保存之后进入自动保存上次填写结果。整理以上所有系统设计方案和规则。

**Result:**
AI 对照实验要求讨论未提交内容的保存与恢复，提出建议并整理项目方案和规则界定。

**修改：**
我先要求查找需求依据，再确认本项目不提供填写草稿自动保存和恢复，并写入规则说明，将实验要求与项目自行约定分开。

### 4. 确定文档嵌入与集合边界

**Prompt:**
接着来思考数据库 MongoDB schema的设计，MongoDB 数据结构应该包含哪些实体、属性和关系？集合与文档如何组织？

**Result:**
AI 提出用户、问卷、答卷三个集合，并说明题目、选项、规则及答案的存储方式。

**修改：**
我认可题目嵌入问卷、答案嵌入答卷的设计，但发现匿名且禁止同一账号重复提交时，原方案缺少独立的资格记录。因此要求增加“参与记录”集合，只记录账号已提交该问卷，不保存答卷 ID，也不向创建者开放。匿名答卷不反向保存参与记录 ID；允许重复时不创建参与记录。

### 5. 将结构设计细化为约束与索引

**Prompt:**
帮我结合问卷业务场景，合理地设计的四个集合中各个字段的约束和索引，给出可执行的schems初始化代码。

**Result:**
AI 补充四个集合的字段、MongoDB 文档验证器、唯一索引及查询索引，并生成可执行的 Schema 初始化代码。

**修改：**
我评估并接受容量上限，要求补齐可执行约束和索引，并明确分工：数据库保护类型、必填项和唯一性，后端检查跳转目标等业务关系。

### 6. 推进后端与前端实现

**Prompt:**
接下来帮我实现业务后端；跑通后解释交互式 API 文档的内容；继续推进前端设计和实现。

**Result:**
AI 协助实现 FastAPI 后端和 React 前端，覆盖账号、问卷编辑与发布、填写提交及统计等流程，并解释接口文档的使用方式。

**修改：**
我以已确认的规则作为实现依据，跑通后追问 API 参数、请求和响应的关系，再要求完善前端，形成可体验的编辑、填写和统计流程。

### 7. 核对 API 契约并完善设计说明

**Prompt:**
请对照 API 说明与后端实现，逐项核对管理 ID 与分享 ID、public 接口登录鉴权、两套 JWT 的用途、JSON 严格类型、PATCH 整体替换、revision 并发控制、提交幂等、错误码、状态机和示例占位符。特别要求每个 public 请求示例补齐 Authorization 头，禁止把 submissionToken 放进该请求头。

**Result:**
AI 对照路由、请求模型和业务服务进行静态核查，确认核心实现已有上述机制。根据我的要求，补齐请求头和发布/关闭示例，增加 ID 对照表、状态操作表及占位符提醒，并修正错误码和幂等边界的表述。

**修改：**
我要求核对：管理路径用 `_id`，分享路径用 `publicId`；登录 `access_token` 放请求头，填写 `submissionToken` 仅放 submit 请求体；错误处理同时看 HTTP status 和 `error.code`。AI 据此补清填写凭据缺失或类型错误的 422、合法结构但 JWT 校验失败的 401，以及同 key 换答案先校验再判冲突；说明已发布未截止时可取消截止、关闭后可确认合法同次重试，并区分未提交答案与问卷草稿、要求示例使用真实 ID 和令牌。此次调整限于 API 与关键逻辑文档，未改后端业务代码。

### 8. 理解 assert 并检查测试覆盖

**Prompt:**
助教建议编写合理且全面的测试用例，再通过 assert 设计测试。这个方法是什么意思？项目适合怎样测试？实验要求的六类测试是否达标？

**Result:**
AI 解释 assert 用于检查实际结果是否满足预期，提出业务规则、API、数据库直接约束、前端逻辑和浏览器流程等测试层次，并整理用例覆盖表。

**修改：**
我先要求解释方法，再提供实验六类要求，要求逐项核对并写清前置条件、步骤和断言，使测试材料对应实验标准。

### 9. 补强数据库直接约束与一致性断言

**Prompt:**
帮我整理用例覆盖表，补强数据库直接约束测试，突出数据一致性断言。

**Result:**
AI 补写绕过 API、直接操作 MongoDB 的约束测试，并增加提交、重复请求、匿名及事务失败等场景的数据一致性检查。

**修改：**
我要求检查数据库实际状态，验证非法写入拒绝及操作前后的一致性。AI 据此增加错误码、索引冲突、记录数量、修订号和文档快照断言，将接口结果与数据变化相互核对。

### 10. 追问并落实关闭与提交竞争测试

**Prompt:**
针对关闭和提交同时竞争的这种竞争情况是否需要进行测试，如何设计测试，给出推荐思路，并按建议落实。

**Result:**
AI 采用受控时序验证“关闭先完成”和“提交先完成”，覆盖匿名/实名、允许/禁止重复提交的组合。专项 8 项通过，包含在完整后端 310 项通过的结果内。

**修改：**
我追问竞争测试的原因和方案，并要求落实。AI 用可复现时序检查冲突、重试、旧版本拒绝及最终数据，保留时序和执行证据。
