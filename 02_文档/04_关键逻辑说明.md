# 问序：关键逻辑说明

本文解释业务规则的执行方式。完整字段与索引见 [数据库设计](02_数据库设计.md)，路由和错误码见 [API 说明](03_API说明.md)。

## 1 执行层次与入口

请求依次经过界面、请求模型、业务服务、领域校验与数据库约束。前端负责交互提示，后端作最终判断。

| 代码 | 职责 |
|---|---|
| [main.py](../01_代码/backend/app/main.py) | 路由、身份依赖、中间件与错误响应 |
| [models.py](../01_代码/backend/app/models.py) | 严格类型、题型结构、容量和时间格式 |
| [security.py](../01_代码/backend/app/security.py) | 用户名规范化、密码哈希、两类 JWT |
| [service.py](../01_代码/backend/app/service.py) | 权限、状态、条件更新、事务与统计 |
| [domain.py](../01_代码/backend/app/domain.py) | 配置、答案、跳转与路径校验，不依赖 HTTP 或数据库 |

## 2 身份与权限

用户名经 NFKC 标准化和去首尾空白，小写结果作为 `usernameKey`，由唯一索引防止重复。密码保持原样，以 Argon2 哈希保存；登录验证哈希，账号不存在也执行 dummy hash 验证。公开响应不返回登录键或密码哈希。

登录 JWT 与填写 JWT 分别验证 `access`、`submission` 用途、签名和有效期，不能互换。除注册、登录及健康检查外，全部业务接口需登录，分享接口也一样。

`owned()` 按问卷 `_id + ownerId` 查询，不存在、ID 非法或不属于本人统一返回 404。答卷和统计也经过此检查；创建者、实名填写者 ID 由服务器赋值，不接受客户端指定。客户端路由守卫仅组织导航。

## 3 状态、冻结与截止

### 3.1 状态与条件更新

| 状态 | 允许操作 |
|---|---|
| `draft` | 保存完整合法配置，可暂存空题目数组；发布至少一道题 |
| `published` | 填写、查看结果；只可改标题、说明及未来截止时间，或取消截止 |
| `closed` | 读取历史答卷与统计，配置只读，不重新开放 |

`publish()` 检查配置及未来截止时间；`patch()` 按实际提供的字段检查，发布后出现 `questions` 或 `settings` 就拒绝，即使值与原来相同。已经到期不能通过取消截止重新开放。

编辑、发布和关闭最终执行 `_id + ownerId + status + revision` 等条件更新，匹配成功才写入并递增 `revision`，否则返回 409。成功新提交和到期状态补齐也可能递增，因此客户端不能按自己的编辑次数推测修订号。冲突时前端保留输入，由用户确认重载。

`revision` 是并发协调号，`schemaVersion` 是结构版本；本阶段没有问卷内容历史版本，依靠发布冻结解释历史答案。

### 3.2 截止与在途请求

截止输入必须带时区，转为 UTC 毫秒精度。`BodyLimitMiddleware` 在请求进入中间件时固定服务器 `received_at`（请求到达时间），提交及事务重试沿用该值，不采用客户端时间，也不等到完整请求体读取后重新计时。新提交需满足：

```text
publishedAt <= received_at
且（deadlineAt 为空，或 received_at < deadlineAt）
```

恰好等于截止时间也拒绝，提前打开页面不产生额外资格。`_expire()` 在读取或操作时补齐过期状态，用数据库当前 `deadlineAt` 写入 `closedAt`；不依赖定时任务，也不删除历史问卷。

事务始终检查截止时间。仅因截止关闭时，截止前到达的在途请求仍可完成。手动关闭与提交则通过同一问卷的条件写入协调先后，处理见第 7 节。

## 4 配置与答案校验

请求模型按题型限制结构，领域函数再检查字段关系：题目 ID 唯一，同题选项 ID、选项文字及规则 ID 不重复；上下限有序；数量不超过选项数；必答题不能配置成无法作答；整数范围内至少存在一个安全整数。未设置的上下限省略，不能传 `null`。

| 题型 | 非空答案与规范化 |
|---|---|
| 单选 | 一个有效选项 ID，不能提交数组 |
| 多选 | 有效选项 ID 数组，无重复且满足数量限制，按选项定义顺序排序 |
| 文本 | 去首尾空白，按 Unicode 码点检查长度 |
| 数字 | 有限整数或浮点数，满足含边界范围；拒绝布尔值、数字字符串、NaN 和无穷大 |

JSON 整数限于 `±(2^53−1)`；整数模式下，浮点输入也必须是安全范围内的整数，保存前转为整数。非法 Unicode 孤立代理字符在模型阶段拒绝。

`null`、全空白文本和空数组统一为空：必答题拒绝，选填题保存 `null` 并跳过长度、数量与范围检查；选填但非空仍执行全部限制。`ensure_size()` 另检查最终 BSON 文档大小。

## 5 跳转与实际路径

### 5.1 规则优先级

`validate_questions()` 建立题目 ID 到数组位置的映射，目标只允许同卷严格后面的题目或结束，避免循环。`_matches()` 解释固定操作符：单选 `eq`，多选 `containsAny/containsAll/setEquals`，数字比较及闭区间 `between`；文本不支持条件跳转。

`_next_index()` 按数组顺序执行第一条命中的规则；空答案不命中，无命中进入下一题。多选按集合比较，“包含全部”允许额外选项，“恰好集合”不允许。最后一题或结束目标只进入提交确认，不自动保存。

### 5.2 完整路径校验

`validate_submission()` 从第一题开始重算，不信任客户端路径：

```text
检查请求中的题目是否存在、是否重复
从第一题开始：
    取答案，缺失按空值处理
    检查必答和题型限制，规范化后加入结果
    按首条命中规则确定下一题
拒绝剩余的路径外答案
返回按实际经过顺序构造的完整答案
```

被跳过的必答题无需作答，也不能夹带该题答案；实际经过但留空的选填题补 `null`。填写接口隐藏 `jumpRules`，由预览计算下一题，但会返回全部题目，跳转不承担题目保密功能。

### 5.3 返回修改与预览

`preview_answers()` 校验已形成路径的连续前缀，返回规范化答案、下一题、是否完成及清除的题目 ID，不写数据库。选填题需显式传空值才能在预览中继续；缺失表示停在该题。

前端 [fill-utils.js](../01_代码/frontend/src/fill-utils.js) 先规范化比较答案：首尾空白、多选顺序和等值数字不算修改。实际修改前题并继续时，[Fill.jsx](../01_代码/frontend/src/pages/Fill.jsx) 发送 `changedQuestionId`，后端与前端同步清空其后答案，即使新路径仍经过某题也要求重填；仅查看则保留。

后端没有更改前的草稿历史，是否真实修改由前端比较并传信号；最终提交仍独立重算。填写答案与凭据仅存本页内存，刷新或退出不恢复；原页登录过期后重新登录仍保留内存状态。

## 6 匿名与重复参与

匿名设置作用于整卷，仍要求登录。实名答卷写当前 `respondentId`，匿名答卷完全省略。只有禁止重复填写时才建立 `{_id,surveyId,userId}` 参与记录，不存答卷 ID、key、答案或额外精确时间；允许重复时不建该记录。

开始填写时的资格查询用于及时提示，最终限制由参与唯一索引和提交事务保证。参与记录不向创建者开放，也不指向具体匿名答卷。

`start()` 生成独立随机 key，签发绑定账号、问卷和 key 的填写 token。token 只在客户端保存，不入库；签名不是加密。匿名保证限于答卷没有直接持久化账号关联，时间与底层日志仍可能用于推断身份，用户自行填写的身份内容也不会自动清除。

答卷查询不返回内部 key，提交成功仅返回通用成功确认。日志不应绑定记录账号、匿名答案、答卷 ID 或填写凭据。

## 7 提交事务、幂等与关闭竞争

### 7.1 两种重复

| 情况 | 最终约束 |
|---|---|
| 同账号主动再填一份 | 禁止重复时以参与记录 `surveyId + userId` 唯一索引限制 |
| 同次双击、并发或网络重试 | 答卷 `surveyId + submissionKey` 唯一索引去重，允许重复问卷也适用 |

`submit()` 验证填写 token 与账号、问卷、key 的绑定，按冻结定义校验并规范化答案，再检查已存在的 key。`_retry_matches()` 比较规范化答案，实名还核对填写者；相同则确认成功，不新增答卷。同 key 更换另一份合法答案返回 `SUBMISSION_KEY_REUSED`，非法载荷先返回 422。合法旧提交可在问卷关闭后确认，但登录与填写凭据仍须有效。

### 7.2 原子写入

所有新提交使用 `session.with_transaction()`，启动时检查 MongoDB 副本集：

```text
入口固定 received_at，验证登录与填写凭据
校验规范化答案；已存在的同次合法提交直接确认
事务内：
    重读问卷并再次检查 key
    检查发布时间、截止、状态与关闭原因
    按当前 revision + status 真实更新问卷，revision 加 1
    禁止重复时插入参与记录
    插入服务端构造的答卷，submittedAt = received_at
事务提交成功后返回成功
```

任何写入失败，参与记录与修订号一并回滚，不会只占资格而没有答卷。事务使用 snapshot 读关注、majority 写关注，15 秒操作预算和 5 秒提交上限；驱动暂态重试沿用原时间与 key。唯一键竞争后重新检查 key，同次已完成则确认，否则按已参与处理。

### 7.3 与关闭建立先后关系

只在事务里读取问卷不能协调另一操作的关闭，因此提交真实更新问卷修订号，与关闭和截止修改争用同一文档。手动关闭先成功则拒绝新提交；提交先取得有效写入资格并完成事务，关闭需按新修订号处理。截止自动关闭仍遵守截止前在途请求的时间规则。

每次提交都写问卷会产生热点竞争，适用于本阶段课程规模。前端在首次发送时固定凭据和答案，结果未知时保留原请求并限制修改，提供“重试原提交”；不能据超时认定服务端未保存。422 可修正，成功后才显示完成；主动再填则取得新 key。

## 8 统计与错误处理

`statistics()` 检查所有权后读取成功答卷，实时聚合，不维护另一份统计集合。总数按答卷计；单题有效数排除 `null`，被跳过题目没有答案元素；多选展开计数，总次数可超过作答数。数字均值用 Decimal128 中间聚合避免有限大数求和溢出，最终返回 JSON 数字，无有效数时为 `null`。答卷和单题内容均分页。

`main.py` 将业务、领域、请求模型及数据库错误转换为统一 `error`，模型错误不回显密码、token 或答案原值。前端 [api.js](../01_代码/frontend/src/api.js) 按业务码处理登录、冲突、校验与重试；401 需区分登录凭据和填写凭据，409 不盲目覆盖，网络错误或 503 保留原提交。完整错误码表见 [API 说明](03_API说明.md)。

验证器负责结构，唯一索引负责键唯一，领域函数负责语义，服务与事务负责权限、状态和跨集合一致性；详细边界见 [数据库设计](02_数据库设计.md)。
